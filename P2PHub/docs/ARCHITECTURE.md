# Архитектура ОСГОворим

> Незнакомые слова смотри в [GLOSSARY.md](GLOSSARY.md).

Этот документ объясняет **как устроена система**: какие части, кто за что
отвечает и как они общаются. Пока без кода — только устройство.

## 1. Главная идея

Обычный сайт работает так: твой браузер ↔ сервер. Сервер хранит всё.

ОСГОворим работает иначе: **устройства пользователей соединяются напрямую** и
обмениваются данными между собой. Сервер нужен по минимуму — только чтобы
помочь пирам найти друг друга.

Обычный сайт — всё через сервер:

```
  [Телефон A] ──► [ Сервер ] ◄── [Телефон B]
                  (хранит всё)
```

ОСГОворим — устройства общаются напрямую:

```
  [Телефон A] ◄═══════════════► [Телефон B]
        ▲      прямое            ▲
        │      соединение        │
        └──────► [Signaling] ◄───┘
            только «знакомит» пиров,
            данные не хранит и не видит
```

## 2. Из чего состоит система

### Клиент (то, что у пользователя)
Это сам сайт/приложение — HTML + CSS + JavaScript. Внутри три основных модуля:

1. **UI (интерфейс)** — экраны: список чатов, окно переписки, кнопка
   «отправить файл», прогресс загрузки.
2. **Модуль сообщений** — отправка/приём текста через WebRTC data channels.
3. **Модуль файлов** — раздача и скачивание файлов через WebTorrent.

### Инфраструктура (минимальная, вспомогательная)

1. **Signaling-сервер** — крошечный сервер. Его единственная задача: когда
   два пира хотят соединиться, передать им «координаты» друг друга. После
   этого они общаются напрямую, и сервер больше не участвует. На старте можно
   брать **публичные** signaling/трекеры, свой поднимем позже.
2. **Трекеры WebTorrent** — помогают найти, у кого есть нужный файл. Тоже
   сначала используем публичные.

> Важно: signaling-сервер **не видит** твои сообщения и файлы — он только
> соединяет пиров. Это и есть смысл децентрализации.

## 3. Как передаётся файл (по шагам)

1. Пользователь A выбирает файл → модуль файлов создаёт «торрент» в браузере
   и получает **magnet-ссылку** (короткий идентификатор файла).
2. A отправляет эту ссылку пользователю B (через чат — то есть через WebRTC).
3. B открывает ссылку → его WebTorrent находит A через трекер и **качает файл
   напрямую** кусочками.
4. Если файл качают несколько человек, они раздают кусочки и друг другу
   (как в обычном торренте) — так быстрее и надёжнее.

## 4. Как передаётся сообщение (по шагам)

1. A и B один раз соединяются через signaling-сервер (обмениваются «координатами»).
2. Между ними поднимается прямой канал WebRTC (data channel).
3. Дальше текст летает напрямую A ↔ B, без сервера.
4. Если собеседник офлайн — сообщение ждёт (в простой версии: пока оба онлайн;
   офлайн-доставку добавим позже, см. ROADMAP).

## 5. Где хранятся данные

- **На сервере — нигде.** Это принцип.
- **В браузере пользователя** — история чатов и список контактов хранятся
  локально (в `localStorage` / `IndexedDB` — встроенные хранилища браузера).
- **Файлы** существуют, пока их кто-то раздаёт (хотя бы один пир онлайн).

## 6. Технологии (стек) и почему они

| Задача | Чем делаем | Почему |
|---|---|---|
| Интерфейс | HTML / CSS / JavaScript | Просто, работает везде, не нужен Mac. |
| Передача файлов | **WebTorrent** | Торрент прямо в браузере, P2P из коробки. |
| Сообщения | **WebRTC** (data channels) | Прямое соединение браузер↔браузер. |
| Знакомство пиров | Signaling (публичный → свой) | Без него пиры не найдут друг друга. |
| Установка на телефон | **PWA** (manifest + service worker) | Ставится на Android и iPhone без Mac. |
| Магазины приложений | **PWABuilder** + GitHub Actions | Сборка под iPhone в облаке, Mac не нужен. |
| История изменений | **Git** | Чтобы ничего не терять и работать командой. |

## 7. Что осознанно НЕ делаем на старте (чтобы не утонуть)

- Свой signaling-сервер (берём публичный).
- Шифрование сообщений «по-взрослому» (WebRTC уже шифрует канал; своё E2E — позже).
- Офлайн-доставку сообщений.
- Аккаунты и регистрацию.

Всё это — в [ROADMAP.md](ROADMAP.md) на более поздние этапы.
